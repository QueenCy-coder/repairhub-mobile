1. Short answer

Yes, the API is linked. Every screen of the app now reads from and writes to the RepairHub API. Nothing is faked or stored only on the phone, except a few things the API has no place for (listed in section 5).

On the live server, only the first steps work today: sign-up, login, customer address and technician registration. Everything after that needs the backend team to set up the server (section 4). Once they do, no app code changes are needed.

2. How it was checked

  • Against the live server’s published API spec: each of the app’s 50 calls was matched against /api-docs.json, with the right method. None are missing.
  • Live server status today: /health answers OK, but it takes about 30 seconds to wake up from sleep. /service-categories and /technician-profiles both return empty lists.
  • Full end-to-end runs against the backend code (Code4Frankie/RepairHub_api, latest commit 57ad3f3) running on a laptop with its own test database. Paystack used the API’s test mode, and uploads were saved locally instead of Cloudinary.
  • Native check on the iPhone Simulator: login, staying signed in after the app is closed, and a repair request with a photo from the photo library, which arrived on the server.
  • I did not create test accounts on the live server; that’s for the team to do.

4. What the backend team needs to do

Blocking Needed before the app works on the live server

  1. Create an admin account on Render. Run ADMIN_EMAIL=… ADMIN_PASSWORD=… npm run seed:admin with the Render MONGO_URI. Admins can’t sign up through the API.
  2. Add the service categories. scripts/seedCategories.js is an empty file, so npm run seed:categories does nothing. The app expects exactly these names:
    • Smartphones, Laptops, Tablets, Desktops, Printers (active)
    • TVs, Refrigerators (inactive, shown as “coming soon”)
    An admin can also create them with POST /service-categories. Cynthia has a ready-made script for this (seed-categories.sh): it asks for the admin email and password and creates them.
  3. Approve technicians. After a technician uploads their ID, an admin approves them with PATCH /technician-profiles/:id/verify {"decision":"approve"}. Until then they can’t see requests or send quotes.
  4. Cloudinary keys on Render (CLOUDINARY_CLOUD_NAME, _API_KEY, _API_SECRET). Request photos, ID documents and dispute evidence all upload there.
  5. Paystack set-up for real payments:
    • Set PAYSTACK_SECRET_KEY (a test key first), and keep PAYSTACK_MOCK off in production.
    • Point the Paystack dashboard webhook to https://repairhub-api-1.onrender.com/api/transactions/webhook/paystack. The app waits for this confirmation before showing “Booking confirmed”.
    • Optionally set PAYSTACK_CALLBACK_URL to a simple “Payment received, return to the app” page.

Should fix Problems found while testing

  • Rate limit vs shared Wi-Fi. The API allows 300 requests per 15 minutes per IP address. The app stays well under that per phone (about 5 requests a minute when idle). But on campus or office Wi-Fi many phones share one IP, so a demo with several people in the same room could hit the limit (“Too many requests”). Consider raising it, or limiting per user instead of per IP.
  • After a full-refund ruling on a dispute, the job becomes cancelled but the repair request stays in_progress (in resolveDispute). The app works around it, but the data is inconsistent.
  • Browser CORS: the live server only allows CLIENT_URL, so the web preview can’t call it from localhost. Phones are not affected. Add test origins, or open it up for development.
  • Cold start: Render’s free tier sleeps. The first request after a quiet period takes about 30 seconds. The app waits up to 70 seconds and shows a message, but a paid instance or a keep-alive ping would make demos smoother.
  • scripts/generatePostman.js is also an empty file.

Nice to have Fields and endpoints the app works around today

  • Preferred date, time and service type on a request: the request schema has no fields for these. The app adds them to the end of problemDescription (“Preferred: Thu 8 Oct · 10:00 AM – 1:00 PM · Home service”) and reads them back. Suggested fields: preferredDate, preferredTime, serviceMode.
  • Technician progress and completion photos: there’s no upload on repair jobs, so the app removed the photo step. Suggested: POST /repair-jobs/:id/media.
  • More job stages: the app has six technician steps (on the way, started, diagnosed, repairing, testing, done). The API’s statuses cover four of them; “Diagnosis completed” and “Repair in progress” are kept only on the technician’s phone. Also, the API has no “on the way” status, so the app uses diagnosing for it.
  • Review replies (a technician answering a review): not available.
  • Password reset by email: not available. The app shows “contact support” for now.
  • Warranty claims for a technician: there’s no “my claims” list, so the app looks up each finished job’s warranty. Suggested: GET /warranty-records/mine. Claim evidence (photos) also isn’t accepted.
  • Names on open requests and reviews: technicians see “Customer” instead of a first name and last initial (e.g. “Ada O.”). Suggested: add customerDisplayName.
  • Missing notifications: when a quote is withdrawn or a request cancelled, the other side gets no notification. The app catches it on its 2-minute refresh.
  • Real push notifications: the API has no device tokens or Expo push. The app checks for new notifications while it’s open.

5. What’s done in the app

Connected to the API

  • Accounts: email + password sign-up and login, no code step. Wrong role, wrong password and duplicate email give clear messages. You stay signed in after closing the app. There’s also change password and log out.
  • Customers:
    • home address saved on the server;
    • request a repair with up to 5 photos and a video, then cancel it or compare real quotes;
    • technician profiles with real ratings and completed jobs;
    • book, then pay by Paystack (card, transfer or USSD) or cash after the repair;
    • reschedule or cancel (refund if paid), track the repair live, confirm and release payment;
    • leave a review, view the warranty and file a claim, report a problem;
    • repair history with refunds and warranties, and a notifications list.
  • Technicians:
    • register skills, areas, ID and certificate; the screen updates by itself when approved or rejected;
    • job board for their categories; send, revise or withdraw quotes;
    • active job with every stage, pause for parts, and an offline queue that sends updates when back online;
    • answer warranty claims (fixed / not covered);
    • earnings, wallet, transactions, reviews, payout account and withdrawals.
  • Staying up to date: every 12 seconds the app checks the newest notification and reloads in full only when something changed, plus a full reload every 2 minutes and after the person’s own actions. This keeps each phone under the API’s rate limit. New notifications show as a banner and a phone notification.
  • Configurable server: the API address lives in .env (live server). Developers can use .env.local to point at their own copy, and tools/run-local-api.mjs runs the backend locally with a test database.

Removed because the API can’t support them yet

  • Sample technicians, automatic quotes and automatic approvals: everything is real now.
  • The ₦2,000 home-service fee. The API charges exactly the quote, so technicians include travel in their price. Commission shows 10%, matching the API.
  • Phone code (OTP) at sign-up, and Google / Apple sign-in.
  • BVN, selfie and PIN checks for payouts. The API only needs bank name, account number and account name; RepairHub’s team pays withdrawals.
  • Technician progress photos, review replies and claim evidence uploads.

Bugs found and fixed during integration

  • The first version would have been blocked by the rate limit within about 3 minutes; polling was redesigned.
  • Photo uploads failed on phones (Expo’s new fetch rejects file parts); uploads now go through the native uploader.
  • Times read wrong: “4:00 – 6:00 PM” was read as 4 AM, and rescheduled visits showed the old time.
  • Preferred date and time were lost after upload, because browsers change line breaks.
  • A technician’s “Diagnosis completed” step could disappear during a refresh or after a pause for parts.
  • Old notifications popped up as new after logging in.
  • A refunded job showed as “Not booked yet”.
  • Wrong technician name and warranty days in history.
  • The warranty-claim alert didn’t clear after it was answered.
  • A stock “after” photo appeared as if the technician took it.
  • Distances showed as “NaN km” (the API has no distances; the app shows areas instead).

Bugs found in this run and fixed

  1. “Revise quote” destroyed the quote. The API has no way to edit a quote, and a withdrawn quote blocks a new one, so the technician lost their quote. Quotes are now final in the app: the technician sees a read-only summary, a clear warning before withdrawing, and a “Quote withdrawn” label afterwards.
  2. A wrong current password signed the user out. The server uses the same 401 code as for an expired login. Now only real session errors end the session.
  3. Technician profile errors: “no reviews yet” despite a review (stale data), the finished repair’s quote shown when opened from search, and an invented “3 months” warranty. All fixed.
  4. The payout account was lost on a new phone. It is now rebuilt from the latest withdrawal.
  5. Earlier repairs couldn’t be claimed on. Once a customer started a new repair, the older warranty vanished from Profile and had no claim button; warranty IDs also changed. Now every completed repair’s warranty is listed (“1 active”), keeps its real ID, shows past claims and their status, and accepts new claims.
  6. Smaller: the Home card hint “finish paying” now reads “pay to confirm”; and the earlier fixes from 8 October (technician redirected to registration after login, note box losing focus).

Not tested

  • A real Paystack payment (only test mode with a locally signed confirmation).
  • The technician’s offline queue on a phone (web has no offline mode), the camera, push notifications and the phone’s location prompt on a real device (the Simulator was used for login and photo upload only).
  • Android, and the live server itself (it has no categories yet).

9. Checklist once the backend is set up

  1. Open the app on two phones with Expo Go: one as a customer, one as a technician.
  2. Technician: create an account, choose Laptops and Smartphones and an area, upload an ID and a certificate.
  3. Admin: approve the technician. Within a few seconds their app unlocks the job board.
  4. Customer: create an account, set an address, request a laptop repair with a photo.
  5. Technician: the request appears; send a quote.
  6. Customer: the quote appears with a notification. Select it, book, and pay with a Paystack test card. “Booking confirmed” appears after Paystack confirms.
  7. Technician: work through the stages to Completed.
  8. Customer: confirm and release, leave a review, open the warranty, file a claim.
  9. Technician: the earnings show the payment minus 10%. Answer the claim, then request a withdrawal.
  10. Admin: mark the withdrawal paid. The technician sees “Paid”.
